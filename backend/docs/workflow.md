# API คำขอซื้อและการจัดส่ง

ใช้ Models (GORM), Controllers (Gin) และ PostgreSQL ตามโครงสร้างใน [คู่มือ Backend](../README.md)
สำหรับการทดลองในเครื่อง ให้ใช้ [Postman Collection](../postman/workflow.postman_collection.json)

## เริ่มทดสอบใน Postman

1. เปิด backend ที่ `http://localhost:8080`
2. Import ไฟล์ `postman/workflow.postman_collection.json`
3. เปิด Collection **T20 - Purchase and Delivery Workflow** แล้วส่งคำขอตามโฟลเดอร์ 1 → 4
4. คำขอสร้างจะเก็บ `order_id` และ `request_id` ที่ระบบสร้างให้ใน Variables อัตโนมัติ

Collection มีการตรวจ HTTP status ในแท็บ Test Results และใช้รหัสข้อมูลตัวอย่าง `DEMO-…`
คำขอ POST/PATCH ใน Collection จะบันทึกข้อมูลลงฐานข้อมูลจริงในเครื่อง
หากใช้ข้อมูลของตัวเอง ให้เปลี่ยน Variables เป็นรหัสจาก API รายการข้อมูล
หากทดสอบค้างไว้จนรถยังติดงาน ให้ส่งงานนั้นจนจบ หรือยกเลิกก่อนเดินทาง แล้วค่อยเริ่มรอบใหม่

เครื่องที่ยังไม่มีข้อมูลตัวอย่าง ให้เตรียม `.env` ตามคู่มือ Backend แล้วรันจากโฟลเดอร์ `backend`:

```powershell
go run ./cmd/seed
```

คำสั่งเพิ่มโรงงาน วัสดุ พนักงาน และรถสำหรับทดลอง โดยใช้รหัส `DEMO-…` และข้ามรายการที่มีรหัสนั้นอยู่แล้ว
seed ใช้ Models ผ่าน GORM ใน `internal/seed/seed.go` และทำงานเมื่อเรียกคำสั่งนี้เท่านั้น
รันซ้ำได้โดยไม่ทับข้อมูลเดิม รวมถึงสถานะรถและงานที่กำลังจัดส่ง
บัญชีตัวอย่างใช้สำหรับความสัมพันธ์ของข้อมูล ไม่มีรหัสสำหรับเข้าสู่ระบบ

## API ที่มี

| Method | URL | หน้าที่ |
|---|---|---|
| GET | `/factories` | รายการโรงงาน |
| POST | `/factories` | เพิ่มโรงงานพร้อมพิกัดบังคับ |
| GET | `/factories/:id` | รายละเอียดโรงงานและพิกัด |
| PATCH | `/factories/:id` | แก้ข้อมูลโรงงานและพิกัด |
| POST | `/locations/search` | ค้นหาสถานที่ รับ JSON `{"query":"นวนคร ปทุมธานี"}` ตอบรายการชื่อ ที่อยู่ latitude และ longitude |
| GET | `/materials` | รายการวัสดุและหน่วย |
| GET | `/sales-staff` | พนักงานขาย เลือก `employee_id` เป็น `sales_staff_id` |
| GET | `/drivers` | คนขับ เลือก `employee_id` เป็น `driver_id` |
| POST | `/drivers` | หัวหน้าขนส่งเพิ่มคนขับพร้อมข้อมูลใบขับขี่ |
| GET | `/drivers/:id` | ข้อมูลคนขับ ใบขับขี่ สถานะ และงานปัจจุบัน |
| PATCH | `/drivers/:id` | แก้ข้อมูลหรือสถานะพนักงาน เก็บประวัติเดิม |
| GET | `/transport-supervisors` | ผู้ดูแลขนส่ง เลือก `user_id` เป็น `supervisor_id` ตาม FK ปัจจุบัน |
| POST | `/purchase-orders` | สร้างคำขอซื้อ คำขอจัดส่ง และรายการวัสดุพร้อมกัน |
| GET | `/purchase-orders` | รายการคำขอซื้อ รองรับ `?status=created` |
| GET | `/purchase-orders/:id` | รายละเอียดคำขอซื้อพร้อมวัสดุและ `request_id` |
| PATCH | `/purchase-orders/:id` | แก้โรงงาน วันที่ หรือวัสดุก่อนจัดรถ |
| GET | `/delivery-requests` | รายการคำขอจัดส่ง รองรับ `?status=pending` |
| GET | `/delivery-requests/:id` | รายละเอียด วัสดุ รถ คนขับ และการยกเลิก |
| PATCH | `/delivery-requests/:id` | แก้ข้อมูลปลายทางและวันที่ก่อนจัดรถ |
| PATCH | `/delivery-requests/:id/assignment` | จัดหรือเปลี่ยนรถ คนขับ และผู้ดูแลก่อนเดินทาง |
| PATCH | `/delivery-requests/:id/status` | ออกเดินทางหรือบันทึกจัดส่งสำเร็จ |
| POST | `/delivery-requests/:id/incidents` | คนขับแจ้งปัญหาและหยุดรอแก้ไข |
| POST | `/delivery-requests/:id/cancellation` | หัวหน้าขนส่งยกเลิกก่อนเดินทางหรือระหว่างหยุดรอแก้ไข |

API รถเดิมยังมี `GET /trucks`, `POST /trucks`, `GET /trucks/:id` และ `PATCH /trucks/:id`
`PATCH /delivery-requests/:id/status` ต้องส่ง `driver_id` ของคนขับที่ได้รับงาน เช่น `{"status":"delivered","driver_id":"DEMO-D001"}` รหัสคนอื่นตอบ 403 ไม่เปลี่ยนสถานะ ผู้ดูแลขนส่งไม่มีปุ่มเริ่มเดินทาง/ส่งสำเร็จในเว็บ
ระบบยังไม่มีล็อกอิน รหัสคนขับใน body จึงไม่ใช่หลักฐานยืนยันตัวตน เมื่อทำ authentication ต้องนำ driver identity จาก session/token มาใช้แทน
ทุก `:id` ในเส้นทางต้องแทนด้วยรหัสจริง เช่น `/purchase-orders/PO-…` หรือ `/delivery-requests/DR-…`

## โรงงานและพิกัด

Import [T20 - Factories](../postman/factories.postman_collection.json) เพื่อทดลอง GET/POST/PATCH โรงงานโดยเฉพาะได้ด้วย
Collection นี้สร้างข้อมูลจริงเมื่อกด Send ให้เปลี่ยนชื่อ ที่อยู่ และพิกัดเป็นข้อมูลที่ต้องการก่อนส่ง

POST `/factories` รับข้อมูลดังนี้ (ไม่ส่ง `factory_id` ระบบสร้างรหัส `FAC-…` ให้):

```json
{
  "company_name": "ชื่อโรงงาน",
  "contact_person": "ผู้ติดต่อ",
  "phone": "0812345678",
  "address": "ที่อยู่โรงงาน",
  "latitude": 13.7563,
  "longitude": 100.5018
}
```

ตัวเลขพิกัดข้างบนเป็นตัวอย่าง ให้ใช้พิกัดโรงงานจริงตอนบันทึก
ทุกช่องข้างบนบังคับกรอก พิกัดต้องเป็นตัวเลขละติจูด -90 ถึง 90 และลองจิจูด -180 ถึง 180
PATCH `/factories/:id` ส่งเฉพาะข้อมูลที่เปลี่ยน แต่ถ้าแก้พิกัดต้องส่งทั้งสองค่า เปลี่ยนรหัสโรงงานไม่ได้
โรงงานเก่าที่ไม่มีพิกัดจะคง `null` ทั้งคู่และข้อมูลเดิม เมื่อแก้ไขโรงงานเก่าต้องเพิ่มพิกัดด้วย
การแก้โรงงานไม่เปลี่ยนข้อมูลในคำขอจัดส่งที่สร้างไว้แล้ว เพื่อให้ปลายทางของงานเดิมคงเดิม
API ใช้ระบบบทบาทเดิมของโครงการที่ยังไม่มี authentication/authorization; ปุ่มเพิ่ม/แก้โรงงานในเว็บแสดงเฉพาะฝ่ายขาย แต่ไม่ได้ป้องกันการเรียก API โดยตรง

## สร้างคำขอซื้อ

ส่ง POST `/purchase-orders` ด้วย Body → raw → JSON:

```json
{
  "factory_id": "DEMO-F001",
  "sales_staff_id": "DEMO-S001",
  "materials": [
    { "material_id": "DEMO-M001", "requested_quantity": 10 },
    { "material_id": "DEMO-M002", "requested_quantity": 20 }
  ]
}
```

เมื่อสำเร็จได้ `201` พร้อม `order_id` และ `request_id`
ระบบสร้างคำขอซื้อสถานะ `created` และคำขอจัดส่งสถานะ `pending` หนึ่งใบที่เชื่อมกัน
ฝ่ายขายเป็นผู้สร้างคำขอ ไม่มีขั้นตอนอนุมัติโดยฝ่ายขาย
รายการวัสดุในคำขอจัดส่งเริ่มต้นตรงกับคำขอซื้อ การบันทึกทั้งหมดอยู่ใน transaction เดียวกัน

ฟิลด์เพิ่มเติมที่ส่งได้:

| ฟิลด์ | ถ้าไม่ส่ง |
|---|---|
| `order_id`, `request_id` | ระบบสร้างรหัสให้ |
| `order_date` | ใช้วันที่ปัจจุบัน รูปแบบ `YYYY-MM-DD` |
| `delivery.request_date` | ใช้วันเดียวกับคำขอซื้อ |
| `delivery.customer_name` | ใช้ชื่อโรงงาน |
| `delivery.address` | ใช้ที่อยู่โรงงาน |
| `delivery.phone_number` | ใช้เบอร์โทรโรงงาน |
| `delivery.destination_latitude`, `delivery.destination_longitude` | ใช้พิกัดที่บันทึกในโรงงาน ถ้าโรงงานยังไม่มีพิกัดจะตอบ 400; หากต้องการปลายทางเฉพาะเที่ยวให้ส่งทั้งสองค่า |

วัสดุต้องมีอย่างน้อยหนึ่งรายการ ห้ามรหัสซ้ำ และจำนวนเป็นจำนวนเต็มมากกว่า 0 ตามชนิดข้อมูลใน Models
วันที่จัดส่งต้องไม่ก่อนวันที่สร้างคำขอซื้อ พิกัดต้องอยู่ในช่วงละติจูด -90 ถึง 90 และลองจิจูด -180 ถึง 180
ยังไม่มีระบบแปลงหน่วย น้ำหนักรวม หรือตัดสต็อก จึงยังไม่คำนวณว่าวัสดุทั้งหมดเกินความจุรถหรือไม่

## แก้ไขก่อนจัดรถ

PATCH `/purchase-orders/:id` รับ `factory_id`, `order_date` และ `materials` โดยส่งเฉพาะสิ่งที่จะเปลี่ยน
หากส่ง `materials` จะใช้รายการที่ส่งแทนรายการเดิมทั้งหมด และอัปเดตวัสดุในคำขอจัดส่งพร้อมกัน
เมื่อเปลี่ยนโรงงาน จะเปลี่ยนชื่อ ที่อยู่ เบอร์โทร และพิกัดปลายทางตามโรงงานใหม่ โรงงานใหม่ต้องมีพิกัดแล้ว
ถ้าส่งรหัสโรงงานเดิม พิกัดปลายทางที่ปรับเฉพาะเที่ยวจะไม่ถูกทับ
เปลี่ยนรหัสคำขอหรือผู้สร้างคำขอผ่าน PATCH ไม่ได้

PATCH `/delivery-requests/:id` รับ `customer_name`, `address`, `phone_number`, `request_date`
และพิกัดทั้งสองค่า ฟิลด์ที่ไม่ส่งจะคงค่าเดิม แต่ละ PATCH ต้องมีอย่างน้อยหนึ่งฟิลด์ และไม่รับ `null`
หากต้องการลบพิกัด ส่ง `{"clear_coordinates":true}` โดยไม่ส่งพิกัดร่วมกัน ส่วน `0,0` ถือเป็นพิกัดจริงเมื่อระบุชัดเจน
GET คำขอจัดส่งและรายการจัดส่งมี `has_coordinates` เพื่อแยกพิกัดที่ระบุไว้จากข้อมูลเดิมที่ยังไม่มีพิกัด
การแก้ข้อมูลคำขอซื้อและปลายทางทำได้เฉพาะตอนคำขอจัดส่งเป็น `pending`

## จัดรถและเปลี่ยนสถานะ

PATCH `/delivery-requests/:id/assignment`:

```json
{
  "truck_id": "DEMO-TR001",
  "driver_id": "DEMO-D001",
  "supervisor_id": "DEMO-USER-SUP"
}
```

รถต้องเป็น `available` และคนขับต้องไม่ติดงานอื่น ระบบจะเปลี่ยนงานและรถเป็น `assigned`
คนขับต้องมีสถานะ `active` และเลขใบขับขี่พร้อมวันหมดอายุที่ยังใช้ได้ในวันที่มอบหมาย (นับวันตามประเทศไทย) รวมถึงการมอบหมายใหม่ระหว่างแก้ปัญหา คนขับเดิมที่ข้อมูลไม่ครบต้องให้หัวหน้าขนส่งเติมที่หน้าพนักงานขับรถก่อนรับงานใหม่
หนึ่งคำขอจัดส่งใช้รถหนึ่งคัน และรถหรือคนขับรับงานที่ยังไม่จบซ้อนกันไม่ได้
เปลี่ยนรถ/คนขับก่อนเดินทางได้ โดยระบบคืนรถเดิมก่อนผูกคันใหม่ใน transaction เดียว

ส่ง PATCH `/delivery-requests/:id/status` ตามลำดับ:

```json
{ "status": "in_transit", "driver_id": "DEMO-D001" }
```

จากนั้นเมื่อส่งเสร็จ:

```json
{ "status": "delivered", "driver_id": "DEMO-D001" }
```

สถานะการจัดส่งคือ `pending` → `assigned` → `in_transit` → `delivered`
คำขอซื้อคงเป็น `created` ระหว่างเตรียมและขนส่ง แล้วเปลี่ยนเป็น `completed` เมื่อส่งเสร็จ
ระบบคืนรถเป็น `available` และล้าง `trucks.request_id` เพื่อรับงานใหม่ แต่ยังเก็บรถและคนขับของงานเดิมใน `delivery_assignments`
การส่งสถานะเดิมซ้ำไม่คืนรถซ้ำจนกระทบงานใหม่

การผูกรถกับงานให้ใช้ API assignment เท่านั้น `POST /trucks` จึงไม่รับ `request_id` ที่มีค่า
ขณะรถติดงาน ไม่สามารถเปลี่ยนสถานะรถโดยตรงผ่าน `PATCH /trucks/:id` ให้ใช้สถานะของคำขอจัดส่ง

## แจ้งและแก้ไขปัญหาระหว่างงาน

คนขับที่ได้รับงานส่ง POST `/delivery-requests/:id/incidents`:

```json
{"driver_id":"DEMO-D001","reason":"breakdown","details":"รถเสียบริเวณหน้าโรงงาน วัสดุยังอยู่บนรถ"}
```

รับตอน `assigned` หรือ `in_transit` เท่านั้น สาเหตุใช้ `breakdown`, `accident`, `destination_unavailable`, `other` รายละเอียดจำเป็นและยาวไม่เกิน 2,000 ตัวอักษร ตอบ `201` พร้อมงานสถานะ `on_hold` และรายการ `incidents` รถและคนขับยังถูกจองไว้ ระหว่างนี้เริ่มเดินทางหรือยืนยันส่งสำเร็จไม่ได้

หัวหน้าขนส่งส่ง PATCH `/delivery-requests/:id/assignment` เพื่อแก้ปัญหา:

```json
{"incident_id":"รหัสจาก incidents","supervisor_id":"DEMO-USER-SUP","truck_id":"รหัสรถที่พร้อม","driver_id":"DEMO-D001","resolution_note":"จัดรถทดแทนและส่งต่อวัสดุเรียบร้อย"}
```

ใช้รถและคนขับเดิมได้เมื่อพร้อมแล้ว หรือเลือกรถใหม่ที่ว่าง ระบบคืนสถานะงานก่อนแจ้งปัญหา และเก็บประวัติรถ/คนขับก่อนเปลี่ยนกับผู้แก้ไขใน `delivery_incidents` รถเดิมที่เสียหรือเกิดอุบัติเหตุคง `maintenance` เมื่อเปลี่ยนรถออก งานหนึ่งยังมีรถปัจจุบันได้คันเดียว การแก้ปัญหาซ้ำด้วยรหัสที่ปิดแล้วตอบ `409`

## ยกเลิกการจัดส่ง

ส่ง POST `/delivery-requests/:id/cancellation`:

```json
{"supervisor_id":"DEMO-USER-SUP","reason":"ประสานฝ่ายขายแล้ว ไม่ดำเนินการจัดส่งครั้งนี้","materials_secured":true}
```

ยกเลิกได้ตอน `pending`, `assigned` หรือ `on_hold` และจะได้ `200` พร้อมรายละเอียดการยกเลิก ต้องระบุหัวหน้าขนส่งและเหตุผล สำหรับงาน `on_hold` ต้องยืนยัน `materials_secured` ว่าประสานฝ่ายขายและจัดการวัสดุแล้ว
คำขอจัดส่งเปลี่ยนเป็น `cancelled` พร้อมคืนรถถ้าจัดรถแล้ว รถที่ซ่อมบำรุงจะไม่ถูกเปลี่ยนเป็นพร้อมใช้งาน คำขอซื้อคงสถานะเดิม ระบบยังไม่มีการเปิดคำขอจัดส่งที่ยกเลิกแล้วใหม่ หากยังต้องส่งต่อให้แก้ปัญหา/เปลี่ยนรถแทนการยกเลิก
ถ้ายังไม่ได้จัดรถ `cancel_requests.truck_id` จะเป็น null ไม่มีการสร้างรหัสรถสมมติ

## สถานะ HTTP และขอบเขตปัจจุบัน

- `200`: อ่าน/แก้ไข/จัดรถ/เปลี่ยนสถานะ/ยกเลิกสำเร็จ
- `201`: สร้างคำขอซื้อและคำขอจัดส่งสำเร็จ
- `400`: ข้อมูลผิดหรือรหัสอ้างอิงไม่มีอยู่จริง
- `404`: ไม่พบคำขอที่ระบุใน URL
- `409`: รหัสซ้ำ ทรัพยากรติดงาน หรือทำขั้นตอนนั้นไม่ได้ในสถานะปัจจุบัน
- `415`: POST/PATCH ไม่ได้ส่ง Content-Type เป็น `application/json`

ชุดนี้เป็น API สำหรับทดสอบในเครื่อง ยังไม่มีล็อกอินและการตรวจสิทธิ์ผู้เรียก
ขณะทดสอบจึงส่งรหัสพนักงานใน Body; เมื่อเพิ่มระบบล็อกอินควรใช้ตัวตนจากระบบยืนยันตัวตนแทน
API โรงงาน วัสดุ และพนักงานในชุดนี้ใช้สำหรับอ่านข้อมูลที่มีอยู่ ส่วนการจัดการข้อมูลเหล่านั้นเป็นงานของแต่ละส่วนในทีม

## การเปลี่ยนแปลงฐานข้อมูล

- คง `delivery_requests.order_id` เป็น unique FK: หนึ่งคำขอซื้อต่อหนึ่งคำขอจัดส่ง
- `supervisor_id` ในคำขอจัดส่งรับ null ระหว่างรอจัดรถ
- `trucks.request_id` เป็น unique index และมี unique index เฉพาะคนขับที่มีงานปัจจุบัน
- `delivery_assignments` หนึ่งแถวต่อคำขอจัดส่งเก็บรถและคนขับที่มอบหมายล่าสุด
- `delivery_incidents` เก็บปัญหา รถและคนขับขณะเกิดเหตุ ผู้แก้ไข และรถ/คนขับที่รับงานต่อ มี unique index ให้มีปัญหาที่ยังไม่แก้ได้หนึ่งรายการต่อคำขอ
- `cancel_requests` เพิ่มเหตุผล ผู้ยกเลิก และการยืนยันจัดการวัสดุ ข้อมูลเก่าคงเดิม
- `cancel_requests.truck_id` รับ null เพื่อยกเลิกงานที่ยังไม่จัดรถได้

การอัปเดตทั้งหมดอยู่ใน transaction ของ `migrations.Run`
หากข้อมูลเดิมมีรถหลายคันผูกคำขอเดียวกันหรือใช้คนขับซ้อนงาน จะหยุดและย้อนการอัปเดต ต้องแก้ข้อมูลที่ขัดกับเงื่อนไขก่อน
